# ТЗ: сервис управления обзвоном

Сверено 2026-09-29 по исходному заданию, ответам Макса и решениям пользователя. Реализация ещё не начата. Исходный контракт имеет приоритет над предположениями; выбранные допущения перечислены в `ASSUMPTIONS.md`, два исходных вопроса закрыты.

## Объём и стек

Две обязательные части: ядро обзвона (разделы 4–6.1) и анализ звонка с UI (раздел 7). NestJS + TypeScript, React 18 + TypeScript + Vite + TailwindCSS, PostgreSQL 16. Clean Architecture с отдельными use case-файлами. Без брокера и Redis: подтверждённой задачи для них нет. Не добавлять регистрацию, управление кампаниями, настоящий дозвон, переанализ, админку и внешнюю LLM.

## Запуск и сдача

`docker compose up -d` из корня: API `localhost:8080`, `GET /healthz` → 200, UI `localhost:5173`, PostgreSQL `postgresql://postgres:postgres@localhost:54329/postgres`. Миграции автоматически при старте. Корневой `.env`: WEBHOOK_SECRET, JWT_SECRET, CRM_URL, PROVIDER_URL. Стенд заменяет `.env`, URL могут быть внешними для Docker. Работа без ключа LLM обязательна. Заглушки разработки — необязательный compose-профиль.

## Ядро

Фиксированные таблицы и поля из раздела 4 сохранить без переименования (см. `docs/database.md`).

`POST /rpc/claim_next_contact`, Bearer JWT HS256 с sub/org_id/role (worker или authenticated), тело `{campaign_id}`. Ответ 200 `{contact: {id, phone_e164, attempt_id}}` либо `{contact: null}`. Выдача именно функцией БД: active-кампания, do_not_call=false, attempts_count<3, локальное время IANA [09:00,20:00), прошло >=4 часа с last_attempt_at либо попыток не было. Создать queued-попытку атомарно с резервированием, заполнив contact_id/campaign_id/org_id. По выбранному соглашению сервис назначает provider_call_id строковым представлением UUID созданной попытки, возвращаемого как attempt_id. До терминального статуса повторная выдача запрещена; автоматического таймаута попытки нет.

`POST /webhooks/calls`: HMAC-SHA256 сырого тела, X-Signature `sha256=<hex>`; неверная подпись →401 до обработки тела. Контракт event_id/call_id/sequence/type/occurred_at/data неизменен. call_id сопоставляется только с сохранённым call_attempts.provider_call_id. Сервис при claim назначает provider_call_id=attempt_id::text; для записей стенда поддерживаются и другие строковые значения без требования равенства id. Неизвестный call_id →404 с кодом CALL_NOT_FOUND, без принятия события.

Типы: call.queued→queued, call.dialing→dialing, call.answered→in_progress, call.completed→completed, call.failed→failed, call.no_answer→no_answer. Все уникальные принятые события сохраняются. Повторы не применяются повторно. Старый sequence не откатывает статус; первый терминальный статус окончательный. Поздний answered может заполнить отсутствующий started_at без изменения терминального статуса. Время берётся из occurred_at, терминальный outcome — из data.

Триггер при первом терминальном переходе увеличивает attempts_count на 1, выставляет last_attempt_at=ended_at и do_not_call=true только при JSON boolean true в outcome.do_not_call. Эти действия и запись outbox атомарны с терминальным переходом.

CRM: отдельный use case и cron обрабатывают outbox; POST непосредственно на CRM_URL с `{attempt_id,status,outcome}`, любой 2xx — успех. Таймауты/отказы CRM не задерживают HTTP-ответ вебхука. Повторы доставки допустимы после потери ответа; повторный вебхук не создаёт второе задание.

Изоляция организаций — API и RLS/права БД, включая доступ напрямую ролью веб-приложения. Логи структурированные, correlation_id проходит от вебхука до сохранённых записей.

## Анализ

POST /api/analyses `{call_attempt_id}` создаёт один анализ на попытку, впервые ответ `{id,status:"queued"}`. Повторный POST возвращает существующий анализ и его фактическое состояние, включая ошибку/отмену; нового обращения к провайдеру нет. GET /api/analyses/:id — состояние и накопленный результат; GET /api/analyses/:id/stream — SSE; POST /api/analyses/:id/cancel — отмена анализа. Все endpoints с JWT, чужая организация →404.

Провайдер: POST `{PROVIDER_URL}/v1/analyze` с `{request_id,transcript}`; ответ text/event-stream с chunk `{field,delta}` и done `{result}`. По уточнению `docs/answer_to_the_question.md` источник выбираем сами: nullable поле `call_attempts.transcript` типа text. Стенд заполняет поле с таким именем, если оно есть. Если значение NULL, пустое или состоит только из пробелов, отправлять фиксированную заглушку «Транскрипт звонка отсутствует. Это тестовая заглушка.»; отсутствие текста не блокирует запуск. Непустой исходный текст передавать без изменения. POST /api/analyses принимает только call_attempt_id, transcript в запросе не требуется.

429: соблюдать Retry-After в секундах, число повторов ограничить конфигурацией. Обрыв после фрагментов →partial, без фрагментов →error; автоматического перезапуска генерации нет. Невалидный done →error, накопленное сохраняется. Cancel останавливает запрос и повторные попытки, сохраняет фрагменты. Разрыв клиентского SSE не отменяет анализ. После сбоя процесса сохранить частичное состояние, не запускать генерацию повторно молча.

SSE chunk/done/error сохраняются в БД; у событий стабильный SSE id, у chunk также id в payload. Last-Event-ID возвращает только продолжение, без повторной генерации. Успешный финал публиковать лишь после валидации общей серверной и клиентской схемой: summary:string, objections:string[], next_step:call_back|send_proposal|disqualify|escalate, lead_score:integer 0..100, confidence:number 0..1.

## UI

Одна страница: ввод JWT и call_attempt_id, запуск анализа, живое отображение и отмена анализа. Генерация JWT локальной CLI-командой, без выдачи секрета браузеру. Никаких дополнительных CRUD-экранов. data-state контейнера: queued, streaming, reconnecting, partial, error, cancelled; дополнительно completed для успеха и idle до запуска. Частичный текст сохраняется при обрыве. Авторизованный SSE-клиент передаёт Authorization и Last-Event-ID.
