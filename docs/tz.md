# ТЗ: сервис управления обзвоном

Сверено с исходным заданием и уточнениями заказчика (в конце документа). Исходный контракт имеет приоритет; принятые допущения — в `ASSUMPTIONS.md`.

## Объём и стек

Две обязательные части: ядро обзвона (разделы 4–6.1) и анализ звонка с UI (раздел 7). NestJS + TypeScript, React 18 + TypeScript + Vite + TailwindCSS, PostgreSQL 16. Clean Architecture с отдельными use case-файлами. Без брокера и Redis: подтверждённой задачи для них нет. Не добавлять регистрацию, управление кампаниями, настоящий дозвон, переанализ, админку и внешнюю LLM.

## Запуск и сдача

`docker compose up -d` из корня: API `localhost:8080`, `GET /healthz` → 200, UI `localhost:5173`, PostgreSQL `postgresql://postgres:postgres@localhost:54329/postgres`. Миграции автоматически при старте. Корневой `.env`: WEBHOOK_SECRET, JWT_SECRET, CRM_URL, PROVIDER_URL. Стенд заменяет `.env`, URL могут быть внешними для Docker. Работа без ключа LLM обязательна. Заглушки разработки — необязательный compose-профиль.

Сдать README.md, ASSUMPTIONS.md, AI-USAGE.md и несквошенную историю Git. README отражает фактический статус, не обещания.

## Ядро

Фиксированные таблицы и поля из раздела 4 сохранить без переименования (см. `docs/database.md`).

`POST /rpc/claim_next_contact`, Bearer JWT HS256 с sub/org_id/role (worker или authenticated), тело `{campaign_id}`. Ответ 200 `{contact: {id, phone_e164, attempt_id}}` либо `{contact: null}`. Выдача именно функцией БД: active-кампания, do_not_call=false, attempts_count<3, локальное время IANA [09:00,20:00), прошло >=4 часа с last_attempt_at либо попыток не было. Создать queued-попытку атомарно с резервированием, заполнив contact_id/campaign_id/org_id. По выбранному соглашению сервис назначает provider_call_id строковым представлением UUID созданной попытки, возвращаемого как attempt_id. До терминального статуса повторная выдача запрещена; автоматического таймаута попытки нет.

`POST /webhooks/calls`: HMAC-SHA256 сырого тела, X-Signature `sha256=<hex>`; неверная подпись →401 до обработки тела. Контракт event_id/call_id/sequence/type/occurred_at/data неизменен. call_id сопоставляется только с сохранённым call_attempts.provider_call_id. Сервис при claim назначает provider_call_id=attempt_id::text; для записей стенда поддерживаются и другие строковые значения без требования равенства id. Неизвестный call_id →404 с кодом CALL_NOT_FOUND, без принятия события.

Типы: call.queued→queued, call.dialing→dialing, call.answered→in_progress, call.completed→completed, call.failed→failed, call.no_answer→no_answer. Все уникальные принятые события сохраняются. Повторы не применяются повторно. Старый sequence не откатывает статус; первый терминальный статус окончательный. Поздний answered может заполнить отсутствующий started_at без изменения терминального статуса. Время берётся из occurred_at, терминальный outcome — из data.

Триггер при первом терминальном переходе увеличивает attempts_count на 1, выставляет last_attempt_at=ended_at и do_not_call=true только при JSON boolean true в outcome.do_not_call. Эти действия и запись outbox атомарны с терминальным переходом.

CRM: отдельный use case и cron обрабатывают outbox; POST непосредственно на CRM_URL с `{attempt_id,status,outcome}`, любой 2xx — успех. Таймауты/отказы CRM не задерживают HTTP-ответ вебхука. Повторы доставки допустимы после потери ответа; повторный вебхук не создаёт второе задание.

Изоляция организаций — API и RLS/права БД, включая доступ напрямую ролью веб-приложения. Логи структурированные, correlation_id проходит от вебхука до сохранённых записей.

## Анализ

POST /api/analyses `{call_attempt_id}` создаёт один анализ на попытку, впервые ответ `{id,status:"queued"}`. Повторный POST возвращает существующий анализ и его фактическое состояние, включая ошибку/отмену; нового обращения к провайдеру нет. GET /api/analyses/:id — состояние и накопленный результат; GET /api/analyses/:id/stream — SSE; POST /api/analyses/:id/cancel — отмена анализа. Все endpoints с JWT, чужая организация →404.

Провайдер: POST `{PROVIDER_URL}/v1/analyze` с `{request_id,transcript}`; ответ text/event-stream с chunk `{field,delta}` и done `{result}`. По уточнению заказчика (раздел «Уточнения заказчика» ниже) источник выбираем сами: nullable поле `call_attempts.transcript` типа text. Стенд заполняет поле с таким именем, если оно есть. Если значение NULL, пустое или состоит только из пробелов, отправлять фиксированную заглушку «Транскрипт звонка отсутствует. Это тестовая заглушка.»; отсутствие текста не блокирует запуск. Непустой исходный текст передавать без изменения. POST /api/analyses принимает только call_attempt_id, transcript в запросе не требуется.

429: соблюдать Retry-After в секундах, число повторов ограничить конфигурацией. Обрыв после фрагментов →partial, без фрагментов →error; автоматического перезапуска генерации нет. Невалидный done →error, накопленное сохраняется. Cancel останавливает запрос и повторные попытки, сохраняет фрагменты. Разрыв клиентского SSE не отменяет анализ. После сбоя процесса сохранить частичное состояние, не запускать генерацию повторно молча.

SSE chunk/done/error сохраняются в БД; у событий стабильный SSE id, у chunk также id в payload. Last-Event-ID возвращает только продолжение, без повторной генерации. Успешный финал публиковать лишь после валидации общей серверной и клиентской схемой: summary:string, objections:string[], next_step:call_back|send_proposal|disqualify|escalate, lead_score:integer 0..100, confidence:number 0..1.

## UI

Одна страница: ввод JWT и call_attempt_id, запуск анализа, живое отображение и отмена. JWT — CLI-командой или dev-эндпоинтом (только при `DEV_TOOLS=true`); секрет в браузер не передаётся. CRUD-экранов нет. data-state контейнера: queued, streaming, reconnecting, partial, error, cancelled; дополнительно completed для успеха и idle до запуска. Частичный текст сохраняется при обрыве. Авторизованный SSE-клиент передаёт Authorization и Last-Event-ID.

## Проверка

Приоритет сначала закончить ядро, затем анализ/UI. Обязательны конкурентные, интеграционные и браузерные проверки контракта. Нагрузочный прогон: 2 млн contacts, 5–20 воркеров, claim p95<=100 мс; webhooks 50 rps, p99<=1 с. Сохранить статистику, ошибки, параметры набора и окружения, включая сценарий медленной/отказывающей CRM. Факт достижения целей определяется измерением.

## Критерии приёмки

- Параллельный claim одного контакта выдаёт его одному воркеру и создаёт ровно одну активную попытку.
- Чужая организация ничего не видит и не меняет ни через API, ни напрямую под ролью веб-приложения; подмена контекста без валидного JWT не открывает RLS.
- `provider_call_id` новой попытки = `attempt_id`; попытки стенда с произвольным `provider_call_id` поддерживаются.
- Неверный HMAC → 401; неизвестный `call_id` → 404 `CALL_NOT_FOUND`, событие не сохраняется.
- Повтор вебхука не применяется повторно; старый `sequence` не откатывает статус; первый терминальный статус окончательный; позднее `answered` может заполнить `started_at`.
- Первый терминальный переход один раз: `attempts_count + 1`, `last_attempt_at`, `do_not_call` по boolean `true`, одна запись CRM outbox — всё в одной транзакции.
- Медленная или недоступная CRM не задерживает ответ вебхука; доставка повторяется и восстанавливается после истечения lease.
- Разбор: один на попытку, без повторной генерации после начала потока; `Last-Event-ID` — только продолжение; наружу уходит только результат, прошедший общую схему.
- JWT, секреты, транскрипт и полный payload не попадают в логи.
- Нагрузочные цели отмечаются выполненными только по результатам измерения (`docs/performance.md`).

### CRM и LLM-провайдер (26.09.2026, ответ 28.09.2026)

**Вопрос.** Здравствуйте, хотел уточнить два момента, 

первый какая crm, так как чтоб корректно вызывать ее методы надо знать ее документацию 

второй про ллм, в документе указано что надо указать url, но итог, так же может чуть разница, если я сделаю url + auth key (какой-нибудь ллмки которая фри доступ) вы сможете запустить таким способом?  И там лимиты так что нагрузить ее не получится, это ок?

**Ответ.** Здравствуйте!

1. CRM. Документация не нужна, потому что это не конкретный продукт. Требуется отправить POST на адрес из CRM_URL с телом { "attempt_id": ..., "status": ..., "outcome": ... } и считать успехом любой ответ 2xx. Всё, что вам нужно знать об этой системе, описано в разделе 6.
При проверке по адресу CRM_URL отвечает наша заглушка: она работает медленно и часть запросов отклоняет. Проектируйте обработку с этим расчётом - см. требование в 6.1 о том, что состояние CRM не должно влиять на приём событий от провайдера.

2. LLM-провайдер. Настоящая модель не нужна, и подключать её не следует.
Провайдер - это наша заглушка, отвечающая по контракту из 7.1: POST {PROVIDER_URL}/v1/analyze, ответ потоком text/event-stream с событиями chunk и done. При проверке мы подставляем в PROVIDER_URL адрес своей реализации, и обращаться к внешним сервисам ваш сервис не должен.
На время разработки напишите собственную заглушку по тому же контракту - это часть задания. Её можно держать в том же docker-compose.yml, но она не должна быть обязательной для запуска: сервис обязан работать с любым адресом, пришедшим в переменной. Удобно вынести её в отдельный профиль, чтобы она не поднималась по умолчанию.
Учтите, что адрес в PROVIDER_URL может указывать за пределы вашей docker-сети.
Ключ авторизации не требуется. Если вы предусмотрите необязательный заголовок для него, то ничего страшного, но работа без ключа должна быть основным режимом. Ограничения по числу запросов тоже неактуальны: наша заглушка их не имеет, зато умеет отвечать отказом с требованием подождать, обрывать поток на середине и возвращать результат, не соответствующий схеме. Именно это и проверяется.
