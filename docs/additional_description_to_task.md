[28.09.2026 13:07] Маx: Здравствуйте!

1. CRM. Документация не нужна, потому что это не конкретный продукт. Требуется отправить POST на адрес из CRM_URL с телом { "attempt_id": ..., "status": ..., "outcome": ... } и считать успехом любой ответ 2xx. Всё, что вам нужно знать об этой системе, описано в разделе 6.
При проверке по адресу CRM_URL отвечает наша заглушка: она работает медленно и часть запросов отклоняет. Проектируйте обработку с этим расчётом - см. требование в 6.1 о том, что состояние CRM не должно влиять на приём событий от провайдера.

2. LLM-провайдер. Настоящая модель не нужна, и подключать её не следует.
Провайдер - это наша заглушка, отвечающая по контракту из 7.1: POST {PROVIDER_URL}/v1/analyze, ответ потоком text/event-stream с событиями chunk и done. При проверке мы подставляем в PROVIDER_URL адрес своей реализации, и обращаться к внешним сервисам ваш сервис не должен.
На время разработки напишите собственную заглушку по тому же контракту - это часть задания. Её можно держать в том же docker-compose.yml, но она не должна быть обязательной для запуска: сервис обязан работать с любым адресом, пришедшим в переменной. Удобно вынести её в отдельный профиль, чтобы она не поднималась по умолчанию.
Учтите, что адрес в PROVIDER_URL может указывать за пределы вашей docker-сети.
Ключ авторизации не требуется. Если вы предусмотрите необязательный заголовок для него, то ничего страшного, но работа без ключа должна быть основным режимом. Ограничения по числу запросов тоже неактуальны: наша заглушка их не имеет, зато умеет отвечать отказом с требованием подождать, обрывать поток на середине и возвращать результат, не соответствующий схеме. Именно это и проверяется.
