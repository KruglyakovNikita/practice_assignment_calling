# P2: нагрузка и проверка по ТЗ — отчёт

Дата: 2026-09-30. Все цифры ниже получены реальными прогонами, скрипты лежат в репозитории.

## Окружение

- Windows 10, Docker Desktop 27.5 (WSL2), Node 22, PostgreSQL 16-alpine из `docker-compose.yml` без тюнинга.
- Генератор нагрузки работает на том же хосте, что и стек.
- **Диск — HDD, не SSD.** Один `COMMIT` с записью стоит 35–200 мс (fsync через WSL2 на HDD, после массовой вставки хуже).
  Это время не зависит от кода: сама функция `claim_next_contact` в БД выполняется за 1.7–2.3 мс.
  **Решение (проверено):** синхронный commit оставлен. Всё превышение 100 мс p95 на этой машине приходится на fsync диска; без него p95 7.7 / 22 мс.

## Данные

Чистый стек (`docker compose -p acclean up -d`, `.env` только с 4 переменными стенда), затем обычный `INSERT` без обходов:
2 000 000 `contacts` в одной кампании, 20 IANA-зон (РФ + мир), `attempts_count` 0..3, половина с `last_attempt_at` за последние 24 ч, 5% `do_not_call`.
В момент прогона подходило под выдачу 522 636 контактов. Вставка 2 млн строк: **3 мин 12 с** (до исправления — ~7 ч, см. ниже).

## claim_next_contact (цель: p95 ≤ 100 мс)

`node scripts/load/claim.mjs --org=<uuid> --campaign=<uuid> --workers=N --seconds=30` — N воркеров в замкнутом цикле, без пауз.

| sync commit, диск в норме (другой прогон, 2M) | 20 | 867 | 21.3 | **36.0** | 49.0 | 0 / 0 |
| sync commit, сразу после 2M-вставки (fsync ~80 мс) | 5 | 46 | 101.7 | 222.6 | 337.1 | 0 / 0 |
| sync commit, сразу после 2M-вставки (fsync ~80 мс) | 20 | 229 | 79.8 | 172.4 | 291.1 | 0 / 0 |
| контроль: `synchronous_commit=off` для роли приложения | 5 | 908 | 5.4 | **7.7** | 10.4 | 0 / 0 |
| контроль: `synchronous_commit=off` для роли приложения | 20 | 1186 | 16.4 | **22.1** | 26.0 | 0 / 0 |

Вывод: сама выдача укладывается в цель с запасом ×4–×10; на хосте с медленным fsync end-to-end p95 определяет диск.
Контрольная строка с `synchronous_commit=off` снималась только для разделения причин, в поставке commit синхронный.

### Что было исправлено (до исправлений на 2M: p50 ≈ 105 мс, p95 ≈ 200–240 мс, рост с числом выдач)

1. **Сид 2M был невозможен.** Триггер проверки таймзоны читал `pg_timezone_names` (≈37 мс/строка → ~7 ч на 2M).
   Теперь справочник снимается один раз в `app_private.timezones` → 0.1 мс/строка.
2. **Скан уже выданных контактов.** Выданные контакты оставались в голове индекса, каждый claim проходил их заново.
   Добавлен маркер `contacts.active_attempt_id` (ведётся только триггерами `call_attempts`: insert/terminal/delete/truncate)
   и частичный индекс `contacts_claim_ready_idx (campaign_id, timezone, coalesce(last_attempt_at,-inf), id) WHERE do_not_call=false AND attempts_count<3 AND active_attempt_id IS NULL`.
3. **Окно времени.** Вместо фильтра `AT TIME ZONE` по всем строкам: loose index scan берёт зоны, реально присутствующие в кампании,
   оставляет те, где сейчас `[09:00,20:00)`, и делает по одной индексной пробе на зону (`LIMIT 1 FOR UPDATE SKIP LOCKED`). Стоимость зависит от числа зон, а не от размера таблицы.
4. **JWT проверялся на каждом подзапросе через RLS** (≈0.3 мс × десятки проб). Функция стала `SECURITY DEFINER`:
   JWT проверяется один раз, все выборки явно фильтруются по `org_id` из проверенного токена.
5. Пул соединений приложения больше не закрывает idle-соединения: новый backend платит ~70 мс за загрузку tz-данных.

## POST /webhooks/calls (цель: p99 ≤ 1 с при 50 rps, CRM не влияет)

`node scripts/load/webhooks.mjs --rps=50 --seconds=60 --drain-seconds=300` — open-loop (фиксированная частота поступления),
каждый звонок: queued → dialing → answered → случайный терминальный, ~10% повторных доставок.
CRM-заглушка в скрипте: ответ через **1.5 с**, **50%** ответов `503`.

| Прогон | rps | Отправлено | Ответы | p50 | p95 | p99 | max | >2 с |
|---|---|---|---|---|---|---|---|---|
| чистый стек + 2M contacts | 49.6 | 2997 | 200 × 2997 | 133 | 280 | **430** | 594 | 0 |
| рабочий стек | 49.7 | 2978 | 200 × 2978 | 129 | 286 | **403** | 642 | 0 |
| запас: 150 rps | 148.8 | 4500 | 200 × 4500 | 485 | 849 | 929 | 1074 | 0 |

CRM: 678 из 682 терминальных уведомлений доставлены за время прогона + 5 мин дренажа, 0 `dead`; 4 оставшихся ждали очередного backoff.
Latency вебхука не зависит от CRM: HTTP к CRM выполняется воркером outbox вне транзакции вебхука.

Исправлено: `CRM_TIMEOUT_MS` был 1500 мс — при CRM медленнее 1.5 с не доставлялось **ничего**, а 8 попыток при 50% отказов теряли ~0.4% уведомлений.
Теперь timeout 10 с, batch 50, до 20 попыток, backoff до 5 мин.

## Функциональная проверка по ТЗ

`node scripts/acceptance.mjs` — black-box: прямые запросы к API и к БД, собственные заглушки CRM/провайдера. Входит в итоговые 82/82 (ниже).
Покрывает: 5 правил выдачи + границы окна, отсутствие повторной выдачи, 30 параллельных claim на 5 контактов, JWT/роли,
изоляцию через API и напрямую через БД-роль веб-приложения (включая поддельный JWT), подпись вебхука, все 6 типов событий,
started_at/ended_at/outcome, дубли, out-of-order, first-terminal-wins, триггер (attempts_count, last_attempt_at, do_not_call), CRM-уведомление и correlation id,
анализ: queued → SSE chunk(id)/done, GET, Last-Event-ID, один вызов провайдера, transcript/fallback, 429 Retry-After, обрыв с/без chunks, невалидный done, отмена, 404 для чужой организации.

Браузер (Chrome, прод-сборка на :5173): зафиксированы переходы `data-state`
`idle→queued→streaming→completed`, `…→partial` (обрыв), `…→error` (невалидный результат), `…→cancelled`,
`streaming→reconnecting→streaming→partial` (рестарт API посреди потока; частичный текст остался на экране).

## Перезапуск под нагрузкой

`node scripts/resilience.mjs --mode=stop|kill`: 120 звонков × 4 события (~40 событий/с, 10% дублей). Отправитель ведёт себя как провайдер: повторяет до 2xx каждые 0.5 с. CRM отклоняет 30% запросов. 12 разборов (3 длинных, ~14 с) с живыми SSE-клиентами, которые переподключаются с `Last-Event-ID`. На 6-й секунде API останавливается, через 5 с запускается снова.

| Проверка | stop (SIGTERM) | kill (SIGKILL) |
|---|---|---|
| ответы 5xx от API | 0 | 0 |
| событий в `webhook_events` на звонок | ровно 4 | ровно 4 |
| терминальный триггер (`attempts_count`) | ровно 1 | ровно 1 |
| строк outbox на звонок / доставлено / dead | 1 / 120 / 0 | 1 / 120 / 0 |
| повторные успешные доставки в CRM | 0 | 0 (at-least-once допускает повтор) |
| вызовов провайдера на разбор | 1 | 1 |
| итог разборов | 8 completed, 4 partial (`WORKER_SHUTDOWN`, не уложились в 5 с grace) | 8 completed, 4 partial (`WORKER_INTERRUPTED`) |
| SSE-клиент vs журнал в БД | совпадает, без пропусков и повторов | совпадает |

Graceful stop занял ~10 с при `stop_grace_period: 30s`.

## Атомарность, ретраи, сбои (`scripts/acceptance.mjs`, секция `atomicity, retries, failures`)

- Сбой внутри транзакции терминального вебхука (запись в outbox принудительно запрещена constraint'ом) → 5xx. Статус, `attempts_count`, `do_not_call`, `webhook_events` и outbox не изменились. Повтор того же события применился ровно один раз.
- 10 параллельных доставок одного события: все 200, сохранено / применено / поставлено в CRM один раз. Два разных терминальных события одновременно: эффекты и CRM-строка один раз.
- CRM `500,500,ok`, `400,ok`, обрыв соединения, timeout > 10 с: все доставлены после неуспешных попыток, в заголовке `Idempotency-Key = attempt_id`, после 2xx повторов нет. `dead` после исчерпания попыток проверен unit-тестом.
- Провайдер внутри разбора: HTTP 500 → `error`; 200 не `text/event-stream` → `error`; битый JSON в chunk после валидного → `partial` с сохранённым chunk; бесконечный 429 → 1 + 3 попытки → `error`; невалидный `Retry-After` → `error`. Разбор, чей воркер упал до начала потока, вернулся в очередь и завершился `completed` одним вызовом провайдера.

Итог: **82/82 PASS**.
