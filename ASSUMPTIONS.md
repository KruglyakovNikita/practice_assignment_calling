# Решения и допущения

## Ядро

- **provider_call_id** при выдаче = `attempt_id::text`: это единственный id, который воркер может передать провайдеру. Попытки, созданные стендом с другим `provider_call_id`, тоже поддерживаются — вебхук ищет только по этому полю.
- **Неизвестный `call_id` → 404 `CALL_NOT_FOUND`**, событие не сохраняется: `webhook_events` привязаны к организации, а без попытки её не определить.
- **Дубли.** Повтор определяется по `event_id` и по паре `(call_id, sequence)` (sequence уникален в пределах звонка). Повтор отвечает 200 и ничего не применяет.
- **Порядок событий.** Статус меняется только событием с `sequence` больше последнего применённого; нетерминальные статусы не откатываются назад; первый терминальный статус окончательный. Позднее `call.answered` может заполнить пустой `started_at`, не меняя статус. Время берётся из `occurred_at`.
- **do_not_call** выставляется только при JSON-значении `true` (не строке `"true"`).
- **Порядок выдачи** ТЗ не задаёт. Внутри таймзоны — сначала без попыток, затем с самым старым `last_attempt_at`; зоны перебираются в случайном порядке. Глобальной сортировки нет: на 2 млн строк она стоила бы сотни мс на claim.
- **Активная попытка не истекает.** Пока попытка не терминальная, контакт не выдаётся (так в ТЗ). Автоматического таймаута нет.
- **Маркер `contacts.active_attempt_id`** — техническое поле, ведётся только триггерами `call_attempts` (insert / терминальный переход / delete / truncate), поэтому попытки, вставленные напрямую SQL, тоже учитываются.
- **claim_next_contact — `SECURITY DEFINER`.** JWT проверяется один раз внутри функции (подпись сверяется в PostgreSQL), все выборки явно фильтруются по `org_id` из токена. Остальной доступ роли веб-приложения — через forced RLS.
- **Роли JWT.** Допускаются только `worker` и `authenticated`; другие → 401. Идентификаторы принимаются в любом формате `8-4-4-4-12` hex, как их принимает PostgreSQL (не только RFC-UUID).
- **CRM.** Transactional outbox, доставка at-least-once (после потери ответа CRM возможен повтор). Timeout 10 с, до 20 попыток с backoff до 5 мин, затем `dead`. Воркер outbox работает в процессе API: отдельный сервис не нужен при измеренной нагрузке.
- **Durability важнее латентности.** `synchronous_commit` не отключается: принятый вебхук и выданная попытка переживают падение БД. Проверено: на HDD fsync одного commit стоит 35–200 мс и поднимает end-to-end p95 claim выше 100 мс (сама выдача — 2 мс; без fsync p95 7.7 / 22 мс). Это ограничение диска, на SSD цель выполняется с запасом (`docs/performance.md`).

## Перезапуск и сбои

- **Graceful stop (SIGTERM, grace 30 с).** Новая работа не берётся; отправленные в CRM запросы дожидаются ответа; разборам даётся до 5 с на завершение; SSE закрываются (клиент продолжает с `Last-Event-ID`). Пулы БД закрываются только после того, как HTTP-сервер обработал активные запросы, поэтому вебхук во время остановки не получает 500.
- **Прерванный разбор.** Поток провайдера ещё не начался (очередь, ожидание `Retry-After`) — разбор возвращается в очередь. Поток шёл — `partial`/`error` без повторного вызова провайдера (ТЗ 7.2). Запрошенная отмена имеет приоритет.
- **SIGKILL.** Транзакция вебхука либо зафиксирована, либо откатана; провайдер повторяет, дубль отсекается. Lease CRM и разборов истекают через 30 с, работу подхватывает новый процесс. CRM — at-least-once, поэтому передаётся `Idempotency-Key: <attempt_id>`.
- **Сбой внутри транзакции вебхука** (например, в outbox) откатывает всё: статус, эффекты триггера, `webhook_events`. Ответ 5xx, повтор провайдера применяется ровно один раз.
- **CRM:** любой не-2xx (включая 4xx), обрыв соединения и timeout 10 с — неуспех с экспоненциальным backoff (1 с … 5 мин, до 20 попыток, затем `dead`). После 2xx уведомление больше не отправляется.

## Разбор звонка

- Анализ разрешён только для терминальной попытки (`completed|failed|no_answer`), иначе 409.
- Один анализ на попытку; повторный POST возвращает существующий с фактическим статусом и не вызывает провайдера.
- **Транскрипт** — nullable колонка `call_attempts.transcript`. NULL/пустой/пробелы → «Транскрипт звонка отсутствует. Это тестовая заглушка.» (только в запросе к провайдеру; колонка не меняется). Непустой текст передаётся как есть.
- **429** повторяется только до начала потока, по `Retry-After` (секунды), не более `ANALYSIS_PROVIDER_MAX_RETRIES` (3) раз.
- **Timeout провайдера** — idle: 30 с без событий. Медленный, но живой поток не обрывается.
- После начала потока генерация не перезапускается: обрыв/timeout с chunks → `partial`, без chunks → `error`; `done` не по схеме → `error`, chunks сохраняются.
- **Валидация ответа провайдера** (схема одна — `packages/contracts`):
  1. Формат SSE: неизвестное событие, не-JSON, chunk без `field`/`delta`, `done` без `result` → `INVALID_PROVIDER_EVENT` (`partial`, если chunks были, иначе `error`).
  2. `done.result` по `analysisResultSchema` до сохранения: несоответствие → `error` / `INVALID_PROVIDER_RESULT`, результат не сохраняется и не уходит клиенту как `done`, chunks остаются.
  3. Клиент повторно проверяет `done` той же схемой.
- **Схема строгая:** лишнее поле, отсутствующее поле, неверный тип, `next_step` вне enum, `lead_score` дробный или вне 0..100, `confidence` вне 0..1 → `error`.
- Отмена сохраняет полученные chunks.
- SSE-журнал хранится в PostgreSQL; `id` события — глобальный bigint, chunk дополнительно несёт тот же `id` в `data`. Отключение клиента не отменяет анализ.
- UI использует fetch-SSE вместо `EventSource`, чтобы передать `Authorization` и `Last-Event-ID`.
- `/dev/*` (JWT любой организации, сид, подпись вебхуков, снимок попытки) есть только при `DEV_TOOLS=true`; UI без него скрывает dev-блоки. Сид идёт под владельцем БД, права ролей приложения не расширяются.
